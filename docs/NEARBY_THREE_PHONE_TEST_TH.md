# ทดสอบการค้นพบและส่งต่อ A → B → C

## สิ่งที่แก้

- การค้นหาแบบกดเองเคยหยุดเมื่อเชื่อมเครื่องแรกสำเร็จ จึงอาจไม่พบเครื่องที่สองที่เปิดให้ค้นพบภายหลัง ตอนนี้ค้นหาต่อจนผู้ใช้หยุด
- โหมดอัตโนมัติเลือกผู้เริ่มเชื่อมตามชื่อเครื่อง เคยข้ามเครื่องชื่อเรียงก่อนตลอด หากเครื่องนั้นเปิดให้ค้นพบอย่างเดียวจะไม่มีฝ่ายเริ่มเชื่อม ตอนนี้ให้ฝ่ายที่ถูกเลือกเริ่มก่อน 2 วินาที จากนั้นลองเชื่อมเองหากยังไม่มีการเชื่อมต่อ
- ลดรอบตรวจอัตโนมัติจาก 8 เป็น 2 วินาที และตัดการหน่วงสุ่ม 200–1,199 มิลลิวินาทีสำหรับชื่อที่ต่างกัน ชื่อเหมือนกันยังมีการหน่วงเพื่อลดการเริ่มพร้อมกัน
- หากพบเครื่องเพิ่มระหว่างกำลังขอเชื่อมเครื่องแรก จะตรวจเครื่องใหม่ต่อโดยไม่ต้องรอรอบ timer

การแก้เหล่านี้ลดการรอในแอป แต่ไม่รับประกันเวลาค้นพบหรือจับมือเชื่อมต่อของ Android บนโทรศัพท์จริง

## เตรียมโทรศัพท์

1. ติดตั้งแอปเวอร์ชันเดียวกันที่รวมการแก้บน Android จริงทั้งสามเครื่อง เรียกเครื่องว่า A, B และ C เพื่อจดผล
2. เปิด Bluetooth, Wi-Fi และบริการตำแหน่ง อนุญาตสิทธิ์ที่แอปร้องขอ เปิดแอปค้างไว้ระหว่างทดสอบ ไม่ต้องเชื่อม Wi-Fi เข้ากับเราเตอร์
3. ปิดอินเทอร์เน็ตมือถือเพื่อยืนยันการส่งออฟไลน์ แต่คง Wi-Fi และ Bluetooth เปิดอยู่
4. หน้าแอปเริ่มโหมดอัตโนมัติได้เอง ให้กด “หยุดการทำงานใกล้เคียง” ทั้งสามเครื่องก่อนตั้งโหมดแบบกดเอง อย่ากดปุ่มค้นหาอัตโนมัติระหว่างชุดทดสอบนี้

## ทดสอบค้นพบสองเครื่องด้วยเครื่องกลาง

1. A และ C กด “เปิดให้ค้นพบ” อย่างเดียว
2. B กด “ค้นหาอุปกรณ์” อย่างเดียว
3. บน B รอให้เจอ A แล้วกดเชื่อมต่อ รอจนแสดงว่าเชื่อมต่อสำเร็จ
4. ตรวจว่า B ยังค้นหาอยู่และพบ C แล้วกดเชื่อม C ด้วย ต้องเห็น B เชื่อมต่ออยู่กับสองเครื่องพร้อมกัน
5. หากต้องการตรวจกรณีพบเครื่องที่สองช้า ให้เริ่มเปิดให้ค้นพบบน C หลังจาก B เชื่อม A สำเร็จแล้ว

การที่ A หรือ C เปิดให้ค้นพบอย่างเดียวแล้วไม่มีรายการอุปกรณ์ที่ค้นพบเป็นพฤติกรรมปกติ เพราะเครื่องนั้นไม่ได้ค้นหา เครื่อง B เป็นผู้ค้นหาและเริ่มเชื่อมทั้งสองลิงก์

## ทดสอบส่งต่อจริง

โครงข่ายที่ต้องการคือ A ↔ B ↔ C โดย A ไม่เชื่อมกับ C โดยตรง การใช้โหมดแบบกดเองด้านบนสร้างโครงข่ายนี้ได้แม้วางทั้งสามเครื่องใกล้กัน เพราะ A และ C ไม่ค้นหากัน อย่าเปิดโหมดอัตโนมัติทั้งสามเครื่องในชุดนี้ มิฉะนั้นอาจเกิดลิงก์ A ↔ C และพิสูจน์การส่งต่อไม่ได้

1. ตรวจ B เชื่อมทั้ง A และ C ส่วน A และ C เชื่อมเฉพาะ B
2. รอการแลกเปลี่ยนรายชื่อและสถานะ ซึ่งระบบส่งซ้ำทุก 5 วินาที อาจต้องหลายรอบ จาก A ต้องเห็น C และสถานะส่งต่อผ่านเครื่องกลาง
3. ใช้หน้าข้อความ เลือกผู้รับ C บน A ส่งข้อความเฉพาะรอบ เช่น `RELAY-001 A to C` การส่งข้อความธรรมดาในชั้น Nearby โดยตรงไม่ได้ทดสอบการส่งต่อของ MessageService
4. ตรวจ C ได้รับข้อความจาก A เพียงครั้งเดียว เส้นทางที่แสดงควรผ่าน B และสถานะบน A เปลี่ยนเป็นส่งถึงเมื่อ ACK กลับผ่าน C → B → A
5. ส่งข้อความจาก C กลับ A เพื่อยืนยันเส้นทางกลับ
6. ทดสอบความจำเป็นของ B: หยุด Nearby บน B ส่งข้อความใหม่จาก A ไป C ต้องยังไม่ถึงทันที จากนั้นเปิดให้ค้นพบบน A/C และค้นหาบน B ใหม่ เชื่อมทั้งสองลิงก์ แล้วตรวจข้อความค้างส่งถึง C

## แยกว่าช้าตรงไหน

จดเวลาของแต่ละช่วงแยกกัน อย่ารวมทุกอย่างเป็น “เชื่อมข้อมูลช้า”

| ช่วง | หลักฐาน | ความหมาย |
|---|---|---|
| เริ่มค้นหา → `Found` | Log ของ B | เวลาค้นพบทางวิทยุ/สิทธิ์/สถานะเครื่องที่เปิดให้ค้นพบ |
| `Connection requested` → `Connection initiated` | Log ของผู้ขอเชื่อม | เวลาตั้งการเชื่อมต่อกับอีกเครื่อง |
| `Connection initiated` → `Connected to` | Log ของทั้งสองฝั่ง | เวลาตอบรับและจับมือของ Nearby |
| เชื่อมแล้ว → มีรายชื่อ C บน A | หน้าข้อความ/สถานะ | การแลกเปลี่ยนข้อมูลตัวตนและรายชื่อผ่าน B มีรอบส่งซ้ำ 5 วินาที |
| ส่งข้อความ → C รับ → A ส่งถึง | ข้อความ/สถานะ/เส้นทาง | การส่งข้อมูลและ ACK ผ่านเครื่องกลาง |

หากค้างใกล้ 30 วินาทีและขึ้น “อีกเครื่องยังไม่ตอบรับ” คือ timeout การเชื่อมต่อ ไม่ใช่การส่งข้อความ ใช้ Log ก่อนข้อความนี้เพื่อดูว่าไม่พบ `Connection initiated` หรือเริ่มแล้วแต่ไม่ถึง `Connected to`

หากยังค้นพบได้เพียงเครื่องเดียวทั้งที่ B ยังแสดงค้นหาอยู่ ต้องเก็บ Log ทั้งสามเครื่อง พร้อมรุ่นโทรศัพท์ เวอร์ชัน Android และเวลาที่กดแต่ละปุ่ม เพื่อแยกปัญหาวิทยุ/สิทธิ์ออกจากโค้ด ไม่สามารถยืนยันสาเหตุฮาร์ดแวร์จากชุดทดสอบจำลองได้
