# ตรวจความเสถียรหลาย node — 6 พฤศจิกายน 2026

ขอบเขต: โทรศัพท์ Android เชื่อมต่อด้วย Nearby P2P_CLUSTER และส่งต่อข้อความผ่านเครื่องกลาง ไม่ใช่การขยายจำนวนเซิร์ฟเวอร์ Supabase

## สิ่งที่แก้

- คิวส่งออกใช้ worker 2 ตัว เมื่อเครื่องใดส่งเสร็จจะส่งให้เครื่องถัดไปทันที เดิมรอให้จบทั้งคู่ก่อนเริ่มคู่ถัดไป จึงเกิดการรอเครื่องช้าโดยไม่จำเป็น ยังคงจำกัด concurrency ของรอบ retry ไว้เท่าเดิม
- จำกัดเวลารอ native enqueue ของข้อความไว้ 5 วินาที เมื่อเกินเวลาจะเข้ากลไก retry เดิม ป้องกันคำสั่ง native ที่ไม่คืนค่าค้างคิวตลอดไป ขีดจำกัดนี้ไม่ใช่เวลารับประกันการส่งถึงปลายทาง และไม่ใช่ timeout ของการส่งไฟล์
- timeout ไม่ยกเลิกงานใน native: แพ็กเก็ตอาจมาถึงภายหลังได้ ระบบจึงยังใช้ ID เดิมและ ACK จากปลายทางเพื่อป้องกันบันทึกซ้ำและไม่อ้างว่าส่งถึงจากผล native เพียงอย่างเดียว

## การตรวจสอบ

- เพิ่ม regression test: กลุ่ม 8 peer มี peer แรกค้าง แต่ peer ลำดับสุดท้ายยังได้รับการส่งสถานะก่อนปล่อย peer แรก และจำนวน send ที่ทำพร้อมกันในรอบนั้นไม่เกิน 2
- เพิ่ม regression test: native enqueue ค้างเกิน 5 วินาทีคืน TimeoutException และส่งครั้งต่อไปได้หลัง native กลับมาทำงาน
- เพิ่มเครือข่ายจำลอง 6 node เชื่อมแบบโซ่และมีวงจรสองวง คิวออฟไลน์ 20 ข้อความกลับมาส่งหลังต่อเชื่อม ตรวจว่าปลายทางมีครบ 20 ข้อความไม่ซ้ำ ต้นทางได้รับ ACK ครบ เครื่องกลางไม่มีแชตของผู้อื่น และทราฟฟิกของตัวจำลองหยุดได้
- ชุดเดิมตรวจการหลุด/ต่อใหม่ การเปิดฐานข้อมูลใหม่ การส่งซ้ำ ACK สูญหาย backoff และเส้นทาง ACK ที่ไม่ถูกต้อง
- analyzer ของไฟล์ที่เปลี่ยนผ่าน ไม่พบปัญหา
- รอบสุดท้ายของชุดเฉพาะส่วนด้านล่างผ่านครบ **100 เคส** ใช้เวลารัน test 48 วินาที หลักฐาน: `output/multi-node-tests-final.log`

การตรวจทั้งโครงการด้วย `flutter test --no-pub` พบผ่าน 346 เคส ข้าม 6 เคส และล้มเหลว 12 เคส ก่อนหยุดรอบที่ค้างใน `guest_mode_flow_test.dart: MemberScreen renders guest mode card and login button` จึงไม่ใช่ผล full-suite ที่ผ่านครบ ความล้มเหลวอยู่ใน chat UI, medical signup, Guest login, messages layout, member screen, responder settings, cloud history comparison และ relay map widget ไม่ได้แก้ส่วนเหล่านั้นในงานนี้ ดูรายละเอียดใน `output/multi-node-full-suite.log` และผล analyzer ใน `output/multi-node-analyze.log` (ไฟล์ output เป็นหลักฐานในเครื่อง ไม่เข้า Git)

คำสั่งตรวจเฉพาะส่วน:

```powershell
.\tool\flutter.ps1 test --no-pub test/message_service_test.dart test/nearby_service_test.dart test/multi_hop_test.dart test/network_presence_sos_test.dart test/nearby_mesh_connection_test.dart test/media_transfer_performance_test.dart
```

## ขอบเขตผลทดสอบและการทดสอบบนมือถือ

ผลข้างต้นใช้ transport จำลองกับ SQLite จริง ไม่ใช่ benchmark ความเร็ววิทยุหรือหลักฐานว่ารองรับมือถือจริง 6–8 เครื่องได้ลื่นทุกสภาพแวดล้อม เวลารัน test รวมการเขียนฐานข้อมูลและการส่งแพ็กเก็ตแบบจำลองตามลำดับ จึงใช้เป็น latency ของมือถือไม่ได้

ก่อนใช้งานภาคสนาม ให้ทดสอบมือถือจริงอย่างน้อย 3 เครื่องแบบ A–B–C ที่ A ติดต่อ C โดยตรงไม่ได้ และ 6 เครื่องแบบมีหลายเส้นทาง เปิดแชต/แผนที่พร้อมส่งข้อความและสื่อ บันทึกเวลาจากส่งจนได้ ACK (median/p95) แยกข้อความและสื่อ ตรวจข้อความซ้ำ ทดสอบปิดเครื่องกลางแล้วเปิดใหม่ และทดสอบต่อเนื่อง 30 นาที ขณะนี้ยังไม่มีผลทดสอบวิทยุจริงหรือค่า p95 จึงยังรับรองว่า “ไม่ช้า” บนอุปกรณ์จริงไม่ได้

ยังมีการกระจายข้อความไปหลายเพื่อนบ้านเมื่อไม่มีปลายทางโดยตรง และรอบ retry ทุก 5 วินาที จึงไม่ใช่ระบบที่รับประกัน latency คงที่เมื่อมีคิวขนาดใหญ่หรือหลายลิงก์เสียพร้อมกัน
