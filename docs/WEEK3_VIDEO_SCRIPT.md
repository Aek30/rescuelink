กำหนดส่ง 10 ตุลาคม 2569 เวลา 23:59 ความยาวแนะนำ 5-7 นาที

## เตรียมก่อนอัด

- เปิดเว็บด้วย `.\tool\flutter.ps1 run -d chrome --web-port=8090` ตัวช่วยโหลด config Supabase ให้
- เปิด Supabase project RescueLink: Authentication > Users และ Table Editor > profiles / account_devices
- ใช้บัญชีทดสอบที่ยอมลบได้ มีอีเมลที่รับลิงก์ยืนยันได้จริง
- ซ้อมสมัคร ยืนยันอีเมล Login อ่าน แก้ชื่อ และลบบัญชีหนึ่งรอบ ก่อนเริ่มอัด
- หากบันทึกจาก build/web ที่สร้างแล้ว ใช้ localhost เพื่อให้ Web Crypto / secure storage ทำงาน
- ไม่โชว์รหัสผ่าน / token / config credentials และไม่แก้ข้อมูลผ่าน Dashboard แทนการทำ CRUD ในแอป

## 1. เกริ่น (20 วินาที)

พูด: “วันนี้นำเสนอ RescueLink สำหรับงาน Advanced Programming Week 3 แอปใช้สำหรับแจ้งเหตุ SOS และสื่อสารออฟไลน์ วันนี้จะสาธิตการเชื่อมฐานข้อมูล Supabase และ CRUD สมาชิกผ่าน Chrome พร้อมอธิบาย schema และระบบซิงก์ข้อมูล”

## 2. Create - สมัครสมาชิก (1 นาที)

ทำ: เปิดหน้าสมัคร กรอกชื่อ `Week3 Demo` อีเมลจริง รหัสผ่านและรหัสยืนยัน สมัครและยืนยันอีเมล หากระบบกำหนด

พูด: “ฟอร์มตรวจข้อมูลก่อนส่งไป Supabase Auth เมื่อสมัครจะมีบัญชีใน auth.users และ trigger สร้างโปรไฟล์ใน profiles โดยใช้ UID เดียวกัน ระบบเก็บรหัสผ่านผ่าน Auth ไม่ได้เก็บรหัสผ่านใน SQLite”

ทำ: เปิด Users และ profiles ชี้ UID กับ id เดียวกัน หาก display_name ยังว่างก่อน Login ให้อธิบายว่าแอปคัดลอกชื่อจากข้อมูลสมัครหลังเข้าสู่ระบบครั้งแรก

## 3. Login และ Read (1 นาที)

ทำ: ลองรหัสผิดให้เห็น error แล้ว Login ด้วยรหัสที่ถูกต้อง Chrome จะเปิดหน้า “ข้อมูลสมาชิก”

พูด: “Login ใช้ signInWithPassword เมื่อสำเร็จได้ session ของบัญชี จากนั้นหน้าโปรไฟล์อ่าน id และ display_name จาก profiles บน Supabase ส่วนอีเมลมาจาก session ของผู้ใช้ ข้อมูลผูกเครื่องบันทึกใน account_devices”

ทำ: ชี้อีเมล UID และชื่อในแอป เทียบ profiles.id / account_devices.user_id กับ UID

## 4. Update (45 วินาที)

ทำ: ลองชื่อว่างให้เห็น validation จากนั้นเปลี่ยนชื่อเป็น `Week3 Updated` และกด “บันทึกข้อมูลสมาชิก”

พูด: “แอปตรวจชื่อไม่ว่างและไม่เกิน 100 ตัวอักษร แล้วอัปเดตเฉพาะแถวของบัญชีปัจจุบัน เมื่อฐานข้อมูลตอบกลับจึงแสดงบันทึกสำเร็จ ใช้ RLS จำกัดการเข้าถึงโปรไฟล์ของตนเอง”

ทำ: Refresh profiles ให้เห็น display_name เปลี่ยน ชี้ id ยังเดิม โหลดใหม่ในแอปเพื่อยืนยันค่าจาก Cloud

## 5. Schema / Sync (1 นาที)

ทำ: เปิด PDF หรือ migration SQL

พูด: “auth.users เชื่อม profiles แบบหนึ่งต่อหนึ่ง และ profiles เชื่อม account_devices กับ sos_records แบบหนึ่งต่อหลาย สำหรับ SOS บันทึกเหตุพร้อมคิว sos_queue ใน SQLite ก่อน เมื่อ Login และออนไลน์ระบบส่งคิวผ่าน sync_sos ใช้เวอร์ชันตรวจข้อมูลขัดแย้ง และใช้ operation_id ป้องกันการส่งซ้ำ ข้อความแชตปัจจุบันเก็บใน SQLite และส่งผ่าน Nearby ยังไม่ซิงก์ข้อความขึ้น Cloud”

## 6. Delete (1 นาที)

ทำ: กด “ลบบัญชีถาวร” อ่านคำอธิบาย กรอกรหัสผ่านบัญชีทดสอบ แล้วกดยืนยัน

พูด: “การลบบัญชีต่างจาก Logout คำขอนี้ส่งไป Edge Function ที่ตรวจ session และรหัสผ่าน ใช้รหัสผู้ใช้ที่เซิร์ฟเวอร์ตรวจได้ ลบไฟล์ Cloud ของเจ้าของ เพิกถอน session และใช้ Admin API ลบบัญชี auth.users จากนั้น foreign key ลบโปรไฟล์และข้อมูลที่เกี่ยวข้อง แอปออกจากบัญชีและลบฐานข้อมูลของบัญชีในเครื่อง กุญแจผู้ดูแลอยู่บนเซิร์ฟเวอร์เท่านั้น”

ทำ: แสดงแอปกลับหน้า Login แล้ว Refresh Users / profiles / account_devices ให้เห็นข้อมูลบัญชีทดสอบหาย ลอง Login เดิมให้เห็นว่าเข้าไม่ได้

## 7. ปิดท้าย (20 วินาที)

พูด: “ได้สาธิต Create, Read, Update และ Delete สมาชิกผ่านหน้าจอและตรวจผลใน Supabase รวมทั้งตัวอย่าง error handling ส่วน schema และรายละเอียดระบบอยู่ใน PDF ที่ส่งประกอบ ขอบคุณครับ/ค่ะ”

## หากพบปัญหาระหว่างซ้อม

- สมัครแล้วแต่ยัง Login ไม่ได้: ยืนยันอีเมลจริงก่อน อย่าอ้างว่าสมัครไม่สำเร็จเพียงเพราะยังไม่มี session
- อีเมลไม่ส่ง / rate limit: ตรวจ Auth SMTP และสถานะ email confirmation ใน Supabase ไม่ปิดยืนยันอีเมลเพียงเพื่อให้เดโมผ่าน
- โหลดโปรไฟล์ไม่สำเร็จ: ตรวจอินเทอร์เน็ต Login และ profiles ของบัญชีนั้น
- ลบบัญชีได้ 403: รหัสผ่านไม่ถูกต้อง บัญชียังไม่ถูกลบ
- ลบบัญชีได้ 401: session หมดอายุหรือ gateway JWT ตรวจไม่ผ่าน ให้ Login ใหม่และตรวจ function logs
- ลบได้ 503: ตรวจ logs ของ delete-account และ Storage/session revocation อย่าลบแถวผ่าน Dashboard มาแทนผลของแอป

การซ้อมครบวงจรบน Cloud จริงยังต้องใช้บัญชีที่ผู้ใช้ยืนยันอีเมลได้ ผล automated tests เป็นหลักฐาน logic / regression ไม่ใช่หลักฐานการส่งอีเมลจริง
